# 工程质量升级（2026-09-24）

## 图像识别增强 v2

证据缓存版本升级为 evidence-2。扫描页、含大面积栅格图的混合页、乱码文本层都会进入 OCR；增加 90 度旋转识别并反算回 PDF 坐标，保留不同读法而不静默覆盖。视觉输入每页包括整页、四个重叠图块，以及最多三个按数字、公差符号、方向和置信度选择的细节区域。单页最多八张图，避免无限裁切。

尺寸引用现在包含服务端解析出的真实原文、页码、坐标、识别方式和置信度；检查虚构 ID、页码不符及数值未匹配，输出待复核说明。模型遗漏主要尺寸引用时，最多增加一次视觉证据定位调用，保持候选尺寸不变。存在引用不等于工程审核通过。

7 张用户部件图 OCR 共提取 264 个文字项，无解析异常；这不是 264 项正确率评测。首轮增强后辊筒关键检查保持 9/9。相关结果保存在 output/vision-enhancement 和 output/vision-enhancement-verified。仍使用现有 DeepSeek Flash，无新增付费服务。

第二轮真实模型复测为 8/9：外径错误输出 159，引用原文却是 (φ154)。10 个字段都有定位信息，2 项引用检查提示异常。已将证据矛盾/无效引用接入审核阻塞，工程师核对并保存对应参数后可解除；不能把这一轮称为通过。30 项回归测试通过，模型抽取稳定性仍需继续改进。

## 已实施的链路

PDF → 逐页文本/本地 OCR → 带坐标与文件哈希的证据包 → 整页和重叠局部图块 → 视觉模型结构化抽取 → 工程中间模型 → 数值校核 → DXF/PDF/SVG → 人工审核 → 工艺生成。

### 解析

`server/evidence.py` 使用 PyMuPDF 提取原生文字；少于 40 个文字项的页面调用 RapidOCR ONNX CPU。每项保留页码、PDF 坐标、识别方式、置信度和稳定 token ID。文件 SHA256 与解析版本用于缓存。OCR 异常不缓存为成功，模型仍可读局部图并收到失败提示。每个送入视觉的页面包含整页及四个有重叠的局部图块；超出图片页预算的页数明确记录，逐页文字仍保留。

当前策略是启发式分流，尚未完成多种 OCR 产品对照；RapidOCR 已实际安装运行。OCR 把直径符号识别为 0 等情况仍存在，因此不能直接成为确认尺寸。尺寸输出引用证据 token，服务端剔除不存在的 ID；存在 ID 也不证明模型归属和解读正确，仍需审核。

### 工程中间模型

`server/engineering_model.py` 生成版本 1.0：对象、单位、尺寸、尺寸状态、原文证据、参考尺寸属性、公差、特征、基准、制造路线、壁厚和放量计算、错误与警告。原料、本件交付、装配后状态分开；目前装配后状态预留为空，未实现完整多工序状态求解器。

生成时写入 geometry；每次导出另存 engineering-model.json，报告接口 `/api/parts/{id}/engineering-model` 根据当前参数重新计算，避免旧报告冒充当前结果。用户锁定参数优先。仍使用旧 geometry 作为 CAD 兼容输入；尚未完全迁移为特征驱动 CAD 数据库。

### 默认最低校核

- 几何数值有限且有效、外径大于内径、空心体内径非零。
- 轴向分段尺寸链闭合；恰好一个已识别段长缺失才允许差值求解。
- 外圆原料=交付尺寸+两侧余量；孔原料=交付尺寸−两侧余量；轴向按端面数计算。
- 已知来料与交付尺寸而未提供余量时，自动差值计算；轴向默认两端对称，保留审核提示。
- 明确的负余量、来料矛盾、加工区域超长、原料/装配后尺寸误作交付尺寸阻止审核。
- 未填写的可选放量为警告，不当成非法数值禁用按钮；工艺生成继承此提示。几何缺失仍阻断。
- 不自动编造未注公差表值、热处理参数或材料。这里的最低要求为软件一致性规则，不是完整标准认证。

### CAD 组合

已运行 build123d/OpenCascade 基础实体校验（圆管、环板、阶梯轴），输出有效性、体积与包围盒；配合现有 ezdxf、统一图面渲染、MLightCAD 在线编辑。新增独立端视图和比例说明。基础实体不包含文字描述的螺纹、槽、倒角，也不替代细节建模校核。

调研 [Text2CAD](https://github.com/SadilKhan/Text2CAD) 和 [CQAsk](https://github.com/OpenOrion/CQAsk)，本次未集成这些自然语言生成代码项目。选择先把确定的参数交给 [build123d](https://github.com/gumyr/build123d)，限制为服务端受控几何操作；未执行模型生成的任意 Python。DWG 仍由现有 ODA 转换，不能称为全开源 DWG 内核。

## 案例验收与实际结果

`tests/fixtures/tube_case.json` 是隔离于生产代码的人工核读数据；生成代码不读取它。`scripts/benchmark_pipeline.py` 先完成真实模型生成，再由 `scripts/evaluate_engineering.py` 对照验收。

本轮使用用户的辊筒参考 PDF，未把预期数值传给模型：9/9 项通过（类型、外径、孔径、长度、参考尺寸属性、孔公差、倒角、左右加工范围）。输出在 `output/engineering-upgrade`。这不是仅从装配图自动拆图的验收，也不代表整套 MBOM、其他部件及工艺已达标。图号缺失、模型文字推算错误、特征表达仍需完善；基础数值通过不等于可直接投产。

## 所需资源

| 资源 | 当前状态 | 需要用户补充 |
|---|---|---|
| 本地 OCR | RapidOCR ONNX CPU 已安装并调用，无 API Key | 暂不需要 |
| 视觉模型 | 使用现有 DeepSeek 配置；支持独立 OpenAI 兼容视觉端点 | 若扩大案例后仍错读，可提供视觉服务 Base URL、模型名称、API Key；密钥仅写本机 .env.local |
| Embedding | 本轮无依赖；企业图纸检索仍为现有方式 | 暂不需要；扩展大规模语义检索时再评测 |
| CAD | build123d 已可运行；在线编辑及 ODA 保留 | 当前不需要；全开源 DWG 兼容性未解决 |
| 工程知识 | 现有标准配置和一致性规则 | 企业认可的标准版本、可用全文/表格、材料与毛坯及余量经验，可进一步提高覆盖率 |

可选依赖固定在 requirements-engineering.txt。环境变量见 .env.example：ENGINEERING_OCR，及 ENGINEERING_VISION_BASE_URL / API_KEY / MODEL。独立视觉提供方必须支持图片输入和 JSON 输出；本轮尚未对第二提供方做实测。

参考：[RapidOCR](https://github.com/RapidAI/RapidOCR)、[PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)。当前部署的是 rapidocr-onnxruntime 1.4.4，不声称已部署 PP-OCRv5/v6。
